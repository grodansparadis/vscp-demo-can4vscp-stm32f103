# How the firmware works

The firmware has three layers:

```text
+--------------------------------------------------------------+
| blinky.c        the node: LED, button, registers, decision   |
|                 matrix, and the callbacks the stack asks for |
+--------------------------------------------------------------+
| vscp-firmware.c the VSCP Level I stack (from the vscp-       |
|                 firmware repository, not changed)            |
+-------------------------------+------------------------------+
| vscp-can.c  events <-> CAN    | persist.c  settings in flash |
+-------------------------------+------------------------------+
| STM32 HAL, generated by STM32CubeMX (Core/, Drivers/)        |
+--------------------------------------------------------------+
```

## The VSCP Level I stack

`vscp-firmware.c` implements what every Level I node must do: nickname
discovery, the standard registers, register read and write, and the other
CLASS1.PROTOCOL events. It is plain C with no hardware knowledge. Everything
that depends on the board it asks for through callback functions that the
application must provide. Its documentation is in the
[vscp-firmware repository](https://github.com/grodansparadis/vscp-firmware/blob/master/docs/vscp-firmware.md).

The callbacks are in two files:

| File | Callbacks |
|------|-----------|
| `vscp-can.c` | `getVSCPFrame()`, `sendVSCPFrame()`: receive and send one event |
| `blinky.c` | Everything else: version, GUID, MDF URL, nickname and control byte storage, application registers (`vscp_readAppReg()`, `vscp_writeAppReg()`), decision matrix info, restore defaults |

The stack does not have its own timer or thread. The application drives it:

- **Every millisecond** (`blinky_tick_1ms()`, called from the SysTick
  interrupt) the counters `vscp_timer`, `vscp_configtimer` and
  `vscp_statuscnt` are increased. The stack uses them for timeouts.
- **In the main loop** (`blinky_work()`) the application fetches an event
  with `vscp_getEvent()` and calls the function that belongs to the state
  the node is in.
- **Every second** `vscp_doOneSecondWork()` is called. It sends the heartbeat.

### Node states

| State | What happens |
|-------|--------------|
| STARTUP | A node with a stored nickname goes active at once. A node without goes to INIT |
| INIT | Nickname discovery (`vscp_handleProbeState()`). The node probes nickname 0 for a segment controller, then 1, 2, 3... until nobody answers, and takes that nickname |
| PREACTIVE | A segment controller answered and will assign the nickname |
| ACTIVE | Normal operation. CLASS1.PROTOCOL events go to `vscp_handleProtocolEvent()`, and every event is fed to the decision matrix |
| ERROR | No free nickname was found |

The status LED on PB12 shows the state: blinking during INIT, steady when
active, off on error.

## CAN transport (`vscp-can.c`)

- `vscp_can_init()` sets a filter that accepts everything, starts the CAN
  controller and enables the receive interrupt.
- The receive interrupt (`HAL_CAN_RxFifo0MsgPendingCallback()`) moves
  extended data frames to a FIFO of 16 frames. Standard frames and remote
  frames are not VSCP and are dropped.
- `getVSCPFrame()` takes a frame from the FIFO and splits the CAN id into
  priority, class, type and nickname with the helpers in
  `vscp-firmware-helper.c`.
- `sendVSCPFrame()` builds the CAN id and puts the frame in a transmit
  mailbox. If all three mailboxes are busy for 20 ms it gives up, and the
  stack counts an error (standard register 0x83).

The CAN controller is set up for automatic retransmission and automatic
bus-off recovery in `firmware.ioc`.

## Persistent storage (`persist.c`)

The STM32F103 has no EEPROM, so the last 1 KB flash page (0x0800FC00) is
used. The linker script keeps the firmware out of that page.

All persistent values are in one structure, `persist_t`, with a copy in RAM
(`g_persist`). The code reads and changes the RAM copy and calls
`persist_changed()`. One second after the last change the main loop writes
the structure to flash. Loading 32 bytes of decision matrix therefore costs
one erase cycle, not 32. A flash page endures at least 10 000 erase cycles.

Erasing and writing the page takes some tens of milliseconds, and the MCU can
not run code from flash meanwhile. The CAN controller keeps receiving on its
own and holds three frames, which is enough at 125 kbit/s for the normal
case. Avoid changing settings many times a second.

If the page holds no valid data (first start), the RAM copy is filled with
0xFF. The stack then sees that its two control bytes are not 0x55/0xAA and
calls `vscp_init_pstorage()`, which sets the defaults.

## The node (`blinky.c`)

- **Blink.** When control bit 7 is set and the interval is not zero, the LED
  is toggled every interval.
- **Button.** The button is sampled every millisecond and must be stable for
  20 ms. Press and release are handed to the main loop, which sends the
  events that are enabled in the control register. Holding the button for two
  seconds drops the nickname and starts a new discovery.
- **Registers.** `vscp_readAppReg()` and `vscp_writeAppReg()` map register
  numbers to `g_persist` and the status and counter variables.
- **Decision matrix.** `do_dm()` compares every received event with the four
  rows and calls `do_action()` for the rows that match.

## Changing the hardware setup with STM32CubeMX

`firmware/firmware.ioc` is an STM32CubeMX project. Open it to change pins,
clock or CAN bit timing and generate the code again. STM32CubeMX keeps the
code between the `USER CODE BEGIN` and `USER CODE END` comments. The project
has user code in three places only:

| File | User code |
|------|-----------|
| `Core/Src/main.c` | `blinky_init()` before the main loop, `blinky_work()` in it, and `__io_putchar()` for the debug output |
| `Core/Src/stm32f1xx_it.c` | `blinky_tick_1ms()` in `SysTick_Handler()` |
| `STM32F103XX_FLASH.ld` | FLASH is 63K instead of 64K, to protect the storage page |

STM32CubeMX may write the linker script again. If the `FLASH` length is back
at 64K after a generation, set it to 63K again.

The top level `CMakeLists.txt` is written once by STM32CubeMX and then left
alone; the user sources and include paths are added there.

## Making your own node from this

1. Describe your node in an MDF: registers, events, decision matrix actions.
2. Change `vscp_readAppReg()` and `vscp_writeAppReg()` for your registers,
   and `persist_t` for the ones that should be stored.
3. Change `do_action()` for your actions.
4. Replace the blink and button code in `blinky_work()` with what your node
   does, and send your events with `vscp_sendEvent()`.
5. Put your MDF on a web server and set its URL in `s_mdf_url`.
6. Set the version in `vscp-projdefs.h`.

## A board with 128 KB flash

Many Blue Pill boards have an STM32F103CB or a C8 that in practice has
128 KB. The firmware works as it is; it just leaves the upper half unused.
